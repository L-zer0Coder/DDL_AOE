# 反攻开发文档

> 本文档汇总反攻阶段的**策略要求、代码现状、已确认的决定、待定项与实施顺序**。
> 策略要求部分以 `反攻策略.md` 为准（那份是从原始策略说明逐字提炼的）；本文档记录"我们讨论出来的东西"和"代码实际情况"。
>
> 维护约定：每确定一条就把它从"待定"移到"已确定"；每完成一项就更新"实施顺序"里的状态。

---

## 一、工程目标

用祭司把敌方**攻城武器厂**转化为己方即获胜（`player[0]->build` 中出现 `BUILDING_SIEGE && isConverted()`）。
失败条件：30 分钟到点 / 祭司死亡（延迟 15 帧判定）/ 市中心曾有过而现在没有。

引擎基本参数：25 帧/秒（`TimePerFrame=40`）；第一波 6000 帧（4 分）、第二波 13500 帧（9 分）、第三波 21000 帧（14 分）；上限 45000 帧（30 分）。

---

## 二、策略要求（摘要，详见 `反攻策略.md`）

1. **军队要达到一定规模才发动，发动前必须集结。**
2. **集结函数必须写**，按"**军队规模 + 帧数**"启动（帧数参考：防御过第三波之后、**24000 帧**左右）。
3. **集结点** = 探路时记录的"被攻击的位置"**或**"视野内出现敌军的位置"，**向自家主营方向退后几格**。
4. **单一集结点不够**（引擎特性：位置附近站满人则认为不可达、发命令人不动）→ 需要**集结区域 3×3~5×5，每点一个兵**；军队移动后空位**可循环填入**。
5. **祭司抵达集结区域**（放**离敌人最远**的一格）+ 周边有足够兵力 → 才可进攻。
6. **进攻不是冲主营**（主营 31 兵、5 箭塔、4 投石车，实力强于玩家）→ 必须**拉扯**：
   - 步骤1：选**最靠近敌方角落**的军队为**突击者**，记录初始坐标；
   - 步骤2：n 格内无敌军 → 向敌方向移动；**被攻击 或 n 格内有敌军** → 向初始位置移动；**突击者移动时其他部队向敌方角落移动 1~2 格**；
   - 步骤3：回到初始位置 → **取消突击者标志**，作为正常军队参战；
   - 步骤4：`info` 中无敌军 → 回到步骤 1；
   - 突击者死亡 → 回到步骤 1 重选。
7. **两种军队配置**：
   - **综合军队**（步弓骑 + 升攻防）：集结时骑兵步兵靠前、弓兵后排；战斗时复合弓**优先打范围内的远程兵**（护祭司）；祭司**转生命值最高的**敌人；战斗 2~3 分钟、祭司能转 5~6 个；**30000 帧（20 分）以上**结束。
   - **复合弓为主**（不升攻防）：前排靠祭司转来的骑兵/方阵（3~5 个）；**理想 27000 帧（18 分）**；风险是被十几个近战近身则主力速亡。
8. **收尾**：拉扯保障后排不被投石车打；清掉其他敌军后，剩两位数复合弓 + 祭司消灭 4 个投石车；然后（或同时）**祭司冲锋转化攻城厂**。祭司满血能抗几轮箭塔；不满血或箭塔密集 → 靠军队吸火，或先拆两三个再进。

## 三、代码现状（对照策略的分析结果）

### 3.1 已经对得上的部分（不用动）

| 策略要求 | 代码位置 |
|---|---|
| 集结点从"被攻击位置"向自家退几格 | `victoryDR/UR` + `pickRallyPoint()`（`RALLY_BACK=6`） |
| 集结区域 5×5、一格一兵 | `RALLY_R=2`；`rallyArmy()` 每帧派 1 个；`rallySlot` 记录格子 |
| 祭司在离敌最远的格 | `rallyPriest()` |
| 兵力够才动 | `rallyEnough()`（`RALLY_NEED=8`） |
| 探路时记录被攻击位置 | `counterAttack` case 1 的斥候段 |

### 3.2 与策略不符 / 缺失的部分

**（1）祭司回不了家 —— 两个独立原因，任一都致命**
- **躲避段挡在回家段前面**：躲避段（`priestExplore` 第 599 行）在危险时无条件 `return`，而回家段在第 644 行；被敌人咬上后每帧都从躲避段返回，回家段永远执行不到 → `priestExploring` 永远为 `true` → 祭司到不了集结区、也不转化。
- **追金矿的筛选条件写反了**（第 681 行）：
  ```cpp
  if(r.Type!=RESOURCE_GAZELLE||(!goldSeen&&r.Type==RESOURCE_GOLD)) continue;
  ```
  按短路求值，当 `r.Type` 是金矿时左边已为 true → 直接 `continue`，**金矿永远不会被选为追踪目标**；`goldSeen` 只能靠探索路过时被动置位。若金矿不在探索路线上，则永远不满足回家条件。
- 附：紧随其后的 `if(r.Blood<=0||r.Cnt<=0)continue;` 对金矿也偏严（金矿的 `Blood` 未必有意义）。

**（2）躲避段的横跳**
候选格是 `priestBlockDR + dirx[k]*6`，**依赖祭司当前位置**；祭司一移动、候选格整体平移，算出的最优格就变，于是每次 AI 运行都判定"目标变了"、重发 `HumanMove` → 路径被反复清掉 → 祭司被钉在原地（两局日志里都出现两点之间来回横跳）。

**（3）集结的三个缺口**
- 启动判据用的是 `Human_Num>=50`（人口，混着农民），**不是"军队规模 + 帧数"**。
- 集结点锚点只有 `victoryDR/UR`（被攻击的位置），**缺"视野内出现敌军的位置"这一路**。
- `rallySlot` 分过格之后**永不重发也不释放**，**没有"军队移动后空位循环填入"**。

**（4）集结期/进攻期 `waveBattle` 仍在派兵打敌人**
`waveBattle` 开头是 `if(counterState<=1 && info.enemy_armies.empty()) return;`，`counterState>=2` 时照常往下执行；而里面的 **1v1 牵制段**和 **spare 派兵段**都没有 `counterState` 判断 → 兵刚被 `rallyArmy` 派去集结区，同帧又被拉去打人 → **集结永远凑不齐**。这与策略第 1 条（发动前必须集结）直接冲突。

**（5）祭司在集结/进攻期不转化**
第 2119 行的转化入口带 `counterState<=1` 门 → 进入集结/进攻后**祭司完全空转**。策略第 7 条要求"战斗时祭司转换敌人"。

**（6）拉扯完全没有**
`counterAttack` 的 `case 3:{ break; }` 是空的。

**（7）进攻期目标选择不符**
- 祭司转化现在是"投石车优先，否则最近"，策略要求**生命值最高**。
- `spare` 段打"最近的敌人"，策略要求复合弓**优先打范围内的远程兵**。
- 备注：代码里已有 `isMeleeSort()` / `isArcherSort()` 两个工具函数（第 498-506 行），**目前全文未被使用**，正好供上面两条使用。

**（8）贴厂缺少前置保护**
`CalmAndCrazy()` 在 `counterState==3` 时直接让祭司去转化工厂，没有"先清投石车 / 看祭司血量 / 军队吸火"的处理。策略第 8 条对此有明确要求。

### 5.3 发现的技术障碍（需要重新商量）

**⚠️ "我军兵数 > 敌兵数 + 5"这条判据，按字面在技术上难以落地**

两个原因：

1. **AI 拿不到"全部敌军"。** `info.enemy_armies` 只返回**我方视野内可见**的敌人。主营内的守军（文档记载 31 兵）只有在我方单位靠近时才可见，斥候不靠近就看不见 → 用"全部"这个词，代码里没有对应的数据源。
2. **数量上可能根本达不到。** 我方人口上限是 50（房子数 × 4，建房条件 `maxNum<50`），其中还要养 20+ 个农民 → 能上战场的兵顶多 20~30 个。而敌方主营有 31 兵 —— **"比对面多 5"（需要 36+ 兵）在人口上限 50 的约束下基本不可能**。

**可选的替代方案（待用户选）**：
- **方案一**：改用**可见敌兵数**（`info.enemy_armies.size()`）——斥候视野内通常只有 1~3 个，条件很容易满足，但含义变成"我方比眼前这几只多 5"，偏保守。
- **方案二**：改用**我方兵数的绝对阈值**（例如"我方兵 ≥ N 个"就开始拉扯），简单可靠，但要重新定 N。
- **方案三**：两者结合（"我方兵 ≥ N" **且** "我方兵 > 可见敌兵 + 5"）。

## 六、实施顺序（开发计划）

### 6.1 开发原则

1. **按依赖推进，不做并行**。祭司到不了集结区，后面全部跑不到；所以"能回家"必须先修。
2. **每一步都要有明确的验证标准**，且尽量做到"一局之内能看出来"。RTS 一局 20~30 分钟，验证方式设计不好会吃掉大半时间。
3. **每步只改一类东西**，改完立刻过语法检查（`g++ -fsyntax-only`），再进下一步。这样出错时能立刻定位到是哪一步引入的。

| **5 进攻期目标选择** | ✅ 已完成 | 新增 `priestConvert()`（在响应范围内优先转**生命值最高**的敌人）、`armyAttack()`（优先打**远程兵**护祭司，用上了 `isArcherSort`）；`trainArmy` 去掉 `counterState<=1` 门（造兵不中断）；`case 3` 里调用 `priestConvert` 使祭司在反攻期也转化 |
| **6 贴厂保护** | ✅ 已完成 | `CalmAndCrazy` 加两道门：①血量不足一半先 `priestFollow` ②离厂超过 `DIS_PRIEST` 先跟随大军；另新增 `priestFollow()`（祭司与部队距离不超过 `PRIEST_HARNESS`=5 格） |

**当前流程**（`counterState`）：

```
0 防守 → 1 等人口到 50 → 2 拉扯（探路记锚点 → 集结 → 引怪歼灭，共 5 轮）→ 3 反攻
                                                                                    ↓
                                     3 反攻: 斥候找攻城厂 → 斥候打"离厂最近的箭塔"
                                            → 大军推进(armyAttack) → 祭司转化(priestConvert)
                                            → CalmAndCrazy 贴厂(血量+距离两道门) → 胜利
```

### 6.2 分阶段计划

#### 阶段 0：先跑一局基线（不改任何代码）

- **目的**：当前代码是 08:38 版，两局日志都是更早的版本跑的，需要确认现状（经济通到哪、祭司死在哪、`counterState` 走到几）。
- **验证标准**：拿到一份"当前版本"的 DebugText。
- **备注**：如果时间紧可以跳过，但后面每一步的"改前/改后"对比就少了一个基准。

#### 阶段 1：让祭司能回家（最关键的先决条件）

- **改动**：`priestExplore` 两处
  1. 躲避段与回家段的**优先级**（现在躲避段无条件 `return`，回家段永远走不到）；
  2. 追金矿的**筛选条件写反**（`r.Type==GOLD` 被短路求值跳过）。
- **验证标准**：跑一局，看祭司是否在满足"凑够活瞪羚 + 见到金矿"后**停止移动并停在箭塔附近**（日志里该有最后一次 `HumanMove`，之后不再有）。
- **风险**：改动虽小，但"谁优先"这个决定会影响祭司遇敌时的行为，需确认不会变成"该躲不躲"。

#### 阶段 2：治躲避横跳（方向锁定）

- **改动**：躲避段的候选格不再依赖祭司当前位置（改为固定方向 + 固定距离），选定目标后锁住，直到走到或判定不可达才重选。
- **验证标准**：日志里**同一段逃跑过程中不再出现反复重发的 `HumanMove`**（当前是两点之间来回切）。
- **备注**：这一项同时改善探索期和未来进攻期的祭司走位，属于"一次修两处"。

#### 阶段 3：让集结真的能完成

- **改动**（四项，按文档逐条对齐）：
  1. `waveBattle` 的 **1v1 牵制段**与 **spare 派兵段**加 `counterState<=1` 锁 → 集结/进攻期不主动出兵（否则集结永远凑不齐）；
  2. `rallySlot` 支持**循环填入**（军队移动后释放格子）；
  3. 启动判据换成**"军队规模 + 帧数"**（待定项 A 的数值 + 24000 帧参考）；
  4. 集结点锚点补上**"视野内出现敌军的位置"**这一路。
- **验证标准**：跑一局，确认能进入 `counterState==2`，且 `rallyEnough()` 能返回真（8 个兵到位、不被 `waveBattle` 拉走）。
- **风险**：这一阶段要跑到第三波之后才看得到，一局耗时长。**必须配合 6.3 的加速手段**。

#### 阶段 4：写拉扯（`case 3`）

- **改动**：实现文档 3.2/3.3 的四步循环 + 突击者死亡的异常处理；用**斥候**当突击者（已定）；初始锚点、前进/撤回判据、"其他部队挪 1~2 格"的协同。
- **验证标准**：能观察到"斥候前出 → 遇敌/被咬 → 退回原位 → 再次前出"的循环，且其他部队在它前进时整体推进 1~2 格。
- **可独立验证**：拉扯只依赖"有几个兵 + 敌军位置"，**不依赖集结完成** → 调试时可临时降低门槛、直接进 `case 3`，用少量兵力单独验证，比等整局快得多。

#### 阶段 5：进攻期的目标选择

- **改动**：
  1. 祭司转化改为**优先生命值最高**（待定项 C：是否加"近战优先"）；
  2. 复合弓/spare 段改为**优先打范围内的远程兵**（用现成的 `isMeleeSort`/`isArcherSort`）；
  3. 放开祭司在**集结/进攻期**的转化门（现在被 `counterState<=1` 挡住）。
- **验证标准**：日志里祭司的 `HumanAction` 目标应落在高血量敌人身上；部队攻击目标应优先落在远程兵。

#### 阶段 6：贴厂保护

- **改动**：`CalmAndCrazy` 之前的准备——先清投石车/箭塔、判断祭司血量、必要时用军队吸火（对齐文档 4.3）。
- **验证标准**：祭司接近攻城厂时，前方投石车已被处理；祭司血量健康时才发起转化。

### 6.3 调试加速手段

一局 20~30 分钟是最大的时间成本，验证时建议：

| 手段 | 说明 |
|---|---|
| **固定地图与旋转** | 启动参数加 `-map map1.njust -rotate 0`，消除"地图/旋转随机"带来的变量，让两次改动可比 |
| **`cheatRes()` / `cheatAction()`** | 调试用：直接加资源、后续命令不消耗时间。**正式评测不可依赖** |
| **临时降低门槛** | 验证单个模块时（如拉扯），临时把 `counterState` 的门槛或初始值改小，一局之内就能看到该模块的行为 |
| **`DebugText` 打点** | 在关键节点（`counterState`、兵数、祭司位置、`rallyEnough` 计数）打印，一局就能定位卡点，避免反复跑局猜原因 |

## 七、技术要点（已核实的判据与字段）

| 用途 | 判据 |
|---|---|
| **"某单位正在被攻击"** | 遍历 `info.enemy_armies`，看有无 `ea.WorkObjectSN == 该单位SN`（斥候段已在用） |
| **"n 格内有敌军"** | 遍历 `info.enemy_armies` 算切比雪夫距离 `max(abs(dx),abs(dy)) <= n` |
| **"单位已到位"** | `abs(a.BlockDR-目标DR)<=1 && abs(a.BlockUR-目标UR)<=1`（与 `farmerAt` 同口径） |
| **"祭司可转化"** | `ConvertCooldown<=0`；且 `NowState!=ATTACKING`（转化中）、`WorkObjectSN!=目标`（已在转） |
| **"科技指令成功"** | 下一帧查 `info.ins_ret[指令id] == ACTION_SUCCESS`；无回执（被每帧条数上限丢弃）视为未成功、下帧重试 |
| **"单位是否空闲"** | `NowState==HUMAN_STATE_IDLE`；注意"扛着货去交货"的农民可能短暂呈现 IDLE，需同时看 `ResourceSort` |

**斥候（`AT_SCOUT`）实测数值**：`BLOOD=60`、`SPEED=4.07`、`VISION=8`、`ATK=3`、`DIS=0`（近战）、`DEFCLOSE/DEFSHOOT=0`。
→ 速度快（与骑兵同级）适合拉扯；血少防 0，本来就无战斗价值，当突击者不亏。
