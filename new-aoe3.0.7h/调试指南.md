# AOE AI 调试实操指南

> 全部内容来自 `new-aoe3.0.7h` 源码实测核对（2026-10-05）。
> 每条都给了源码位置，不是猜的。

---

## 0. 三个核心抓手（先记住这三个就够了）

| 抓手 | 用途 | 代价 |
|---|---|---|
| `DebugText(QString)` | 屏幕左侧打印，实时看 AI 状态 | 会刷屏，需自己加节流 |
| `-ResultLogFile a.txt` | 每帧写一行 JSON 到文件，可做曲线 | 文件会很大 |
| `-map / -rotate` | 固定地图和朝向 | 必须加，否则每局都不一样 |

## 1. 命令行参数（GlobalVariate.cpp:682-800 `ParseArguments`）

已实测存在的参数：

```bash
release/newAOE.exe -map map1.njust -rotate 0 -ResultLogFile run.txt -freq 4
```

| 参数 | 作用 | 源码位置 |
|---|---|---|
| `-map map1.njust` | 固定地图。**不加就随机**（Map.cpp:2324-2335） | :774 |
| `-rotate 0` | 顺时针旋转，只能是 `0/90/180/270`。**不加就随机**（:790-795） | :778 |
| `-ResultLogFile a.txt` | 每帧一行 JSON：frame/time/wood/food/gold/stone/score | :758 |
| `-freq MAX` | 加速（`1\|2\|4\|8\|MAX`） | :768 |
| `-record` | 录制指令流到文件 | :747 |
| `-RecordOutputFile f` | 指定录像文件 | :763 |
| `-offscreen` | 关渲染，纯跑速度（**批量验证必用**） | :754 |
| `-exam` | 考试模式（会屏蔽部分 debug 输出，别用） | :750 |

**调试第一条铁律：永远写死 `-map` 和 `-rotate`。** 否则每次跑都是不同地图不同朝向，
你根本没法对比两局之间的差异。

```bash
# 固定调试环境的标准命令
release/newAOE.exe -map map1.njust -rotate 0 -ResultLogFile dbg.txt -freq 4
```

## 2. 屏幕打印：DebugText

### 用法（ai.h:66-74, AI.cpp:128-131）
```cpp
DebugText(QString("[GATE] stock=%1 gazelleSt=%2 wood=%3")
    .arg(stockNum).arg(gazelleState).arg(info.Wood));
```

输出格式固定是 `" UsrAI打印：xxx"`，颜色 black（AI.cpp:130）。

### 关键坑：filterRepetitionMessage（GlobalVariate.cpp:514）
```cpp
if(!filterRepetitionMessage || debugMessageRecord[content]==0 || color=="black" || color=="green")
```
`color=="black"` 才绕过去重。所以 **`DebugText` 打的字不会因重复被吞掉**，
但引擎自己的 `call_debugText("red", ...)` 会（红字只在第一次出现时显示）。

### 节流写法（你自己控制，别用帧数）
```cpp
static int lastWood=-1;
if(info.Wood!=lastWood){          // 只在"变化了"时才打
    lastWood=info.Wood;
    DebugText(QString("[ECON] wood=%1 meat=%2 gold=%3 farm=%4")
        .arg(info.Wood).arg(info.Meat).arg(info.Gold).arg(farmNum));
}
```
> 颜色可以用 black 之外的颜色吗？`AI::DebugText` 内部写死 `"black"`，
> 想上色要直接调 `call_debugText("red", 内容, id)`（你项目 manageBuild 里 `:994`
> 就是这么用的）。

## 3. 日志文件：ResultLogFile

### 格式（GlobalVariate.cpp:847-862）
每帧一行紧凑 JSON：
```json
{"win":false,"time":400,"frame":10000,"score":0,"wood":120,"food":45,"gold":0,"stone":0}
```
| 字段 | 含义 |
|---|---|
| `frame` | 帧号（**记得 25 帧/秒**，TimePerFrame=40） |
| `time` | `frame*40` 毫秒 |
| `wood/food/gold/stone` | 四种资源 |

### 用法：转 CSV 画曲线
日志是 JSON-lines，但字段固定，用 `jq` 或 python 都能秒转：

```bash
# 转 CSV（jq）
cat run.txt | jq -r '[.frame,.wood,.food,.gold,.stone] | @csv' > run.csv
```
拿到 CSV 就能丢进 Excel / matplotlib 画"木-肉-金随帧变化"，**卡点一目了然**。

### 局限（很重要）
- **只记录资源，不记录指令**。要看"发了什么指令"得靠 `--record`。
- 只有结局时才 `LogOut`？→ 不，它是每帧调用，但 30 分钟一局约 4.5 万行，
  文件不大但也别 MAX 速跑几十分钟。

## 4. 指令录像：-record（最强证据链）

```bash
release/newAOE.exe -map map1.njust -rotate 0 -record -RecordOutputFile rec.bin
```
`ProcessGameRecord`（Core.cpp:1396）在**每条指令执行前**录像。
配合 `logActionResult`（Core.cpp:931）——它会把**成功的指令**翻译成人话：
```
HumanMove:农民 12 移动至 (350.0, 470.0)
BuildAction:兵营 5 执行行动 ACTION_2
HumanBuild:农民 3 开始在块坐标 (45,60) 处建造 Building_1001
```
**注意 `logActionResult` 第一行：`if (ret != ACTION_SUCCESS) return;`
它只打成功的，失败的静默丢弃** —— 所以"日志里没反应"就是失败或被丢弃，
这是本项目最重要的调试抓手之一（大量 ACTION_INVALID_* 在这里看不见）。

## 5. 针对性排查：验证"指令被丢弃"（本项目最可疑的点）

### 背景（Core.cpp:1388-1390）
```cpp
int ObjCnt = self->build.size() + self->human.size();
while (!NowIns->instructions.empty() && ObjCnt--) { ... }
```
**每帧硬上限 = 建筑数 + 人口数**，超出的指令被静默丢弃、**不写 ins_ret**。

### 怎么验证
在 `processData()` **开头**加一条：
```cpp
// 统计本帧打算发多少条指令 vs 引擎能处理多少条
static int overLog=-1;
int budget = (int)info.buildings.size() + (int)info.farmers.size() + (int)info.armies.size();
if(budget!=overLog){
    overLog=budget;
    DebugText(QString("[BUDGET] buildings=%1 farmers=%2 armies=%3 -> 上限%4")
        .arg(info.buildings.size()).arg(info.farmers.size()).arg(info.armies.size()).arg(budget));
}
```
再在 `manageBuild` 各派活段落里数实际发出了几条。如果**发出数 > 上限**，
那就坐实了"指令被丢弃"——这就是我推断的经济崩盘根因 1。

## 7. 关键判据速查（决定"该不该发指令"）

| 想知道 | 看什么 | 陷阱 |
|---|---|---|
| 村民是否空闲 | `f.NowState==HUMAN_STATE_IDLE` | `WorkObjectSN==-1` 只在**建筑**用，单位没这字段 |
| 建筑是否空闲 | `b.Project==ACT_NULL` | `Project` 同时也是箭塔的攻击目标字段（Core.cpp:599-603） |
| 建筑是否盖好 | `b.Percent>=100` | |
| 资源够不够 | `info.Wood/Meat/Gold/Stone` | |
| 人口有没有满 | `info.Human_Num<info.Human_MaxNum` | 后勤科技后是 0.5/单位，**用 double 比较** |
| 指令成功没 | `info.ins_ret[id]==ACTION_SUCCESS` | **被丢弃的指令没有回执**（Core.cpp:1390） |
| 某资源还有货吗 | `r.Cnt>0`（瞪羚用 `r.Blood>0`） | |

## 8. 一套标准调试流程

```bash
# 第 1 步：固定环境
release/newAOE.exe -map map1.njust -rotate 0 -ResultLogFile dbg.txt

# 第 2 步：加 3 条 DebugText（开头状态 / 末尾汇总 / 派活计数）

# 第 3 步：跑 3-5 分钟，看屏幕
#   - 闲人是否长期 >0          → 人力浪费
#   - 建造链卡在哪一环        → 缺什么
#   - 科技 flag 卡在哪        → 资源不够还是被丢弃
#   - 派活数 vs [BUDGET] 上限 → 指令被丢弃

# 第 4 步：需要精确证据时开录像
release/newAOE.exe -map map1.njust -rotate 0 -record -RecordOutputFile rec.bin

# 第 5 步：批量验证（无渲染，快 10 倍）
release/newAOE.exe -map map1.njust -rotate 0 -offscreen -freq MAX -ResultLogFile run.txt
```

## 9. 常见坑（都是我实际读源码确认过的）

1. **地图/朝向随机**（Map.cpp:2324, GlobalVariate.cpp:788-799）→ 不写死就没法对比两局。
2. **`HandleGameOver()` 直接 `exit(0)`** → 胜负一判进程立刻退出，看不到后续日志。
3. **`ins_ret` 是跨帧持久的**（GlobalVariate.cpp:1054-1063 会继承上帧，最多 100 条），
   不是每帧清空。查旧指令 id 可能查到**历史**回执。
4. **`logActionResult` 只打成功**（Core.cpp:933）→ 日志里没有 = 失败或被丢弃，两者要靠别的手段区分。
5. **每帧指令上限**（Core.cpp:1388）→ 超限静默丢弃且无回执，这是最难查的坑。
6. **`Project` 双重含义**：箭塔存的是攻击目标，其他建筑存的是当前行动（Core.cpp:599-607）。
7. **`-exam` 会屏蔽 debug 输出**（GlobalVariate.cpp:512）→ 调试时别加这个参数。
8. **`-freq MAX` 配 `-ResultLogFile`** → 文件行数暴涨，但总量其实可控（一局约 4.5 万行）。
